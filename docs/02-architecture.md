# 시스템 아키텍처 — RepoView

## 1. 전체 구성

```
[React 프론트엔드]  ──HTTP/SSE──>  [FastAPI 백엔드]
                                        │
                ┌───────────────┬───────┼───────┬───────────────┐
                │               │       │       │               │
          Agent Orchestrator  Tool Layer│  Repo Indexer      Embedder
           (직접 짠 루프)    (LLM이 호출)│ (구조 스캔)      (청킹·임베딩)
                │               │       │       │               │
           [OpenAI API]    [로컬 레포 파일]   [SQLite]      [SQLite + Chroma]
```

## 2. 컴포넌트별 역할

| 컴포넌트 | 역할 |
|---|---|
| **Repo Indexer** | 질문 처리와 분리된 사전 작업. 레포 디렉토리를 스캔해 파일 트리·언어/프레임워크 감지 결과를 SQLite에 저장한다. 매 질문마다 도는 것이 아니라 레포당 1회 실행한다. `python -m repoview.index`. |
| **Embedder** (Phase 3부터) | Repo Indexer와 분리된 별도 사전 작업. 코드 파일을 청크로 쪼개 OpenAI 임베딩 API로 벡터화해 Chroma에 넣는다. `python -m repoview.embed`. Repo Indexer와 분리한 이유는 아래 4절 참고. |
| **Tool Layer** | LLM이 호출할 수 있는 함수들(`list_directory`, `search_code`, `search_semantic`, `read_file`). 각 도구는 순수 함수로 두고 에이전트와 분리해 단위 테스트가 가능하게 한다. 레포 개요는 도구가 아니라 시스템 프롬프트에 주입한다(→ `05-agent-design.md`). |
| **Agent Orchestrator** | 직접 구현한 루프. 대화 상태 관리, 도구 호출 디스패치, 반복 횟수·토큰 상한 제어, 종료 판단, 트레이스 기록을 담당한다. |
| **LLM Client** | OpenAI 호출 래퍼. 재시도(429/5xx), 토큰·비용 집계. |
| **Eval Runner** | 웹 앱과 별개로 도는 오프라인 스크립트. 고정 질문 셋을 에이전트에 돌려 탐지율을 측정한다. |

## 3. 저장소

- **SQLite** — 레포 메타데이터, 세션/메시지, 에이전트 트레이스(도구 호출 이력), eval 실행 결과.
- **Chroma** — 코드 청크 임베딩 (Phase 3부터). 벡터 검색만 담당.

### SQLite를 선택한 이유

저장 대상이 레포 2개 메타데이터, 세션/메시지 수백 건, 트레이스 로그, eval 결과 정도로 수만 행 규모를 넘지 않고, 로컬 단일 사용자 도구라 동시 쓰기 경합도 없다. Postgres를 도입하면 데모 실행 때마다 별도 DB 프로세스(Docker 등)를 띄워야 하는 비용만 늘고 얻는 것이 없다고 판단했다.

검토한 대안은 **Postgres + pgvector**였다. 관계형 데이터와 벡터를 한 DB에서 처리해 Chroma를 스택에서 뺄 수 있다는 장점이 있지만, "clone 받고 바로 실행"이라는 로컬 데모 편의성을 우선해 SQLite + Chroma 조합을 유지한다.

## 4. Embedder — 청킹·임베딩 (Phase 3)

### Repo Indexer와 분리한 이유

구조 스캔(파일 트리, 언어 감지)은 빠르고 무료지만, 임베딩은 OpenAI API 호출이 필요해 시간과 비용이 든다. 두 작업을 하나의 명령으로 묶으면 구조만 다시 확인하고 싶을 때도 매번 임베딩 API를 호출하게 된다. `python -m repoview.index`(구조)와 `python -m repoview.embed`(임베딩)를 분리해, 코드가 실제로 바뀌었을 때만 임베딩을 다시 돌리도록 했다.

### 청킹 전략

파일을 50줄 단위로, 앞뒤 10줄씩 겹치게 슬라이딩 윈도우로 쪼갠다(50줄 미만 파일은 파일 전체가 청크 하나). 함수/클래스 경계를 인식하는 AST 기반 청킹도 검토했지만, Java와 TypeScript 두 언어 각각에 파서를 유지보수해야 하는 비용이 이 프로젝트 규모에 비해 크다고 판단했다. 청크 경계가 함수 중간에서 잘려도 겹치는 구간이 있으면 의미가 크게 훼손되지 않는다. 대상 파일 집합은 Task 4에서 이미 구현한 `iter_code_files`를 그대로 재사용해, 검색 대상과 임베딩 대상을 동일하게 유지한다.

### 재임베딩 전략

`python -m repoview.embed`를 실행할 때마다 해당 레포의 Chroma 컬렉션을 통째로 지우고 처음부터 다시 임베딩한다(Task 6의 `repo_file` DELETE-then-reinsert와 동일한 패턴). 파일 해시를 비교해 바뀐 파일만 재임베딩하는 증분 방식도 검토했지만, 두 레포 합쳐 약 750개 파일 규모에서는 전체 재구축도 OpenAI 임베딩 비용이 몇 센트 수준이라 증분 로직의 복잡도를 정당화하지 못한다고 판단했다.

## 5. 질의 처리 흐름

1. 프론트에서 질문 전송 → 백엔드가 세션 생성
2. 레포 개요 + 시스템 프롬프트 구성
3. 에이전트 루프: OpenAI 호출 → `tool_calls` 응답 → Tool Layer 실행 → 결과를 대화에 append → 반복
4. 각 스텝을 SSE로 프론트에 실시간 스트리밍(에이전트가 어떤 도구를 왜 호출했는지 화면에 그대로 노출) + SQLite 트레이스 테이블에 기록
5. 모델이 도구 호출 없이 최종 텍스트를 내놓으면 종료 → 파일:라인 인용이 포함된 리뷰를 렌더링

## 6. 에러 처리 / 안전장치

- **반복 횟수 하드캡**(초안은 15턴이었으나 실제로는 6턴 — 판단 이유는 `docs/05-agent-design.md` §3 참고) 초과 시 중단하고 "여기까지 찾은 것" 부분 결과를 반환한다.
- **질의당 토큰 상한** 초과 시 동일하게 처리해 비용 폭주를 방지한다.
- 도구 실패(파일 없음, 검색 타임아웃)는 예외로 터뜨리지 않고 `tool_result`에 에러 메시지로 담아 반환한다 → 에이전트가 스스로 복구를 시도할 수 있다.
- **경로 탈출 방어**: `read_file`/`list_directory`의 인자는 LLM이 생성하므로, 허용된 레포 루트 밖으로 나가는 경로(`../../etc/passwd` 류)는 차단한다. 도구 인자를 신뢰 경계로 취급한다.

## 7. Phase별로 추가되는 것

| Phase | 추가 컴포넌트 |
|---|---|
| 1 | Repo Indexer(트리/언어 감지), FastAPI 스켈레톤, 프론트 셸 |
| 2 | `search_code`/`read_file` 도구 + 단순 LLM 리뷰 |
| 3 | Embedder(청킹·임베딩), Chroma, `search_semantic` 도구, 프롬프트 검색 전략 가이드 |
| 4 | 전체 에이전트 루프(반복 제어, 트레이스) — 실제로는 Phase 3 구현에 흡수됨. SSE 스트리밍은 이 표와 무관하게 훨씬 나중에 별도 작업으로 추가됨(`docs/04-api-spec.md` §2). "Phase 4"라는 이름은 이후 안전장치 라운드가 재사용해서, 이 표의 정의와 다른 걸 가리키는 경우가 있다 — `docs/01-prd.md`의 "용어 안내" 참고. |
