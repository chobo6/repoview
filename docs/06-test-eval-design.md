# 테스트 / Eval 설계 — RepoView

성격이 다른 두 가지를 분리한다. **테스트**는 결정론적으로 검증 가능한 코드를 대상으로 하고, **Eval**은 비결정적인 LLM 출력 품질을 측정한다.

## A. 테스트 (결정론적 영역)

핵심 원칙: 비결정적인 부분(모델 응답)과 결정적인 부분(루프 제어·도구 실행)을 분리하고, 후자를 확실히 테스트한다.

| 대상 | 테스트 내용 |
|---|---|
| **Tool Layer** | `search_code` 패턴 매칭, `read_file` 라인 범위·200줄 상한·없는 파일 에러 처리, `list_directory` 제외 규칙 |
| **Embedder (Phase 3)** | 청킹 함수의 경계 계산(50줄 단위, 10줄 겹침, 50줄 미만 파일은 통째로 청크 1개) — 순수 함수라 임베딩 API 없이 결정론적으로 검증 가능 |
| **경로 탈출 방어** | `../../etc/passwd`, 절대경로, 심볼릭 링크가 모두 거부되는지 (보안 경계라 필수) |
| **Agent 루프** | Fake LLM 클라이언트를 주입해 미리 정한 `tool_calls` 시퀀스를 반환시키고, 루프 동작·`CAPPED` 전환·반복 감지·트레이스 기록을 API 호출 없이 검증 |
| **인용 검증기** | 없는 파일 인용, 라인 범위 초과, 읽지 않은 파일 인용을 각각 잡아내는지 |
| **API** | FastAPI TestClient로 세션 생성 → SSE → `done` 이벤트까지 (fake LLM 사용) |

### 픽스처

도구 테스트는 실제 LocalQuest/Songpyeon 대신 `tests/fixtures/mini_repo/`라는 작은 가짜 레포를 만들어 사용한다. 실제 레포를 쓰면 테스트가 느리고, 원본 코드가 바뀔 때마다 테스트가 깨진다.

### Fake LLM을 쓰는 이유

에이전트 루프의 제어 로직(반복 상한, 반복 호출 감지, 트레이스 기록, 에러 복구)은 모델 응답과 무관하게 결정론적이다. 미리 정한 응답 시퀀스를 돌려주는 Fake 클라이언트를 주입하면 이 로직 전체를 API 비용 없이, 빠르고 반복 가능하게 검증할 수 있다.

### Fake Embedding Client (Phase 3)

같은 이유로 임베딩 API도 테스트에서는 고정된 벡터를 반환하는 Fake 클라이언트로 대체한다. `search_semantic`의 "쿼리 임베딩과 저장된 청크 임베딩 중 가장 가까운 것을 반환한다"는 로직 자체는 결정론적이므로, 실제 임베딩 값이 의미상 정확한지가 아니라 유사도 계산·top_k 정렬·메타데이터 반환이 올바른지를 검증하는 데는 Fake로 충분하다.

## B. Eval (비결정적 영역 — 품질 측정)

### 1. eval 셋 구성 (목표 20~30 케이스)

| 유형 | 내용 |
|---|---|
| **실제 사례** (`is_planted=0`) | LocalQuest: 인코딩 깨짐, 관리자 공지 404 / Songpyeon: CJS·ESM 이중 로드, 재접속 시 onAuth 미재호출 취약점, `.dockerignore` 재귀 매칭 누락 |
| **심은 버그** (`is_planted=1`) | N+1 쿼리, 하드코딩된 시크릿, 인덱스 없는 대용량 조회, 동기 블로킹 호출 |
| **네거티브 케이스** | 문제가 없는 코드에 "여기 성능 문제 있어?"라고 물었을 때 없다고 답하는지 |

네거티브 케이스가 없으면 "일단 전부 문제라고 지적하기" 전략이 탐지율 100%를 받는다. 반드시 포함한다.

### 2. 채점

- **LLM-as-judge**: `expected_finding`과 실제 리뷰를 판정 모델이 대조한다. 판정 모델은 피평가 모델과 분리한다(같은 모델이 자기 답을 채점하면 편향이 생긴다).
- **규칙 기반 보조**: `expected_file_path`가 리뷰의 인용에 실제로 포함됐는지 확인한다.
- **최종 판정**: `judge가 YES` AND `인용 파일 일치`. 위치까지 맞아야 탐지로 인정한다. 엄격한 기준이 지표의 신뢰도를 만든다.

### 3. 지표

| 지표 | 의미 |
|---|---|
| 탐지율(Recall) | 정답 케이스 중 찾아낸 비율 |
| 오탐율(FPR) | 네거티브 케이스에서 없는 문제를 지적한 비율 |
| 인용 정확도 | 리뷰의 파일:라인 인용 중 실제 존재하는 비율 = 할루시네이션 지표 |
| 비용/지연 | 케이스당 평균 토큰·달러·소요 시간·반복 횟수 |

탐지율만 보면 "전부 지적하기"가 이기므로 오탐율과 함께 읽어야 한다.

### 4. 실행 및 비교

- `python -m repoview.eval --repo <name> --phase <2|3>` → `eval_run` 생성, 케이스별로 세션을 실행하고 결과를 저장한다. (PRD 초안엔 Phase 4까지 비교한다고 적혀 있었지만, "Phase 4"는 이후 실제 구현에서 "Agent 핵심 기능"이 아니라 "안전장치 라운드"를 가리키는 이름으로 굳어졌고 `--phase` 플래그는 `2`/`3`만 받는다 — 아래 "판단 이유" 참고.)
- Phase 2 / 3을 각각 돌려 비교표를 만든다.
- LLM 응답에 비결정성이 있으므로 초기 측정은 1회, **최종 비교표를 만들 때만 케이스당 3회 평균**을 낸다 — 실제로 3회 반복해보니 탐지율이 실행마다 흔들리는 걸 확인했다(`docs/TROUBLESHOOTING.md` 참고). "Phase 3이 Phase 2보다 통계적으로 유의미하게 낫다"고 단정할 만큼 표본이 크진 않다는 게 현재까지의 정직한 결론이다.

### 5. 과적합 방지 (설계만, 실제 적용 안 함)

eval 셋을 보면서 프롬프트를 튜닝하면 그 셋에만 잘 맞는 결과가 나온다. 원래 설계는 케이스의 70%만 튜닝에 쓰고 30%는 마지막 최종 측정에만 쓰는 것(train/test 분리)이었지만, 실제로는 케이스 수가 작고(레포당 17~19개) 프롬프트 자체를 eval 셋 보면서 반복 튜닝하지 않았기 때문에 이 분리를 적용하지 않았다. eval 셋 규모를 더 키우고 프롬프트 튜닝을 본격적으로 시작하면 이때 다시 고려할 것.

### 판단 이유 — "Phase 4"라는 이름이 두 가지 뜻으로 쓰인 이유

PRD(`docs/01-prd.md`) 원안의 Phase 4는 "Agent 핵심 기능"(function calling 자율 루프)이었다. 그런데 실제 구현 순서상 이 자율 루프는 Phase 3(RAG) 작업과 함께 이미 완성됐고 `config.CURRENT_PHASE = 3`로 굳어졌다 — 별도로 "Phase 4"라는 실행 모드를 만들 필요가 없었다. 그 뒤 반복 호출 감지·토큰 상한·인용 사후검증 같은 안전장치를 추가하는 라운드가 있었는데, 이때 "Phase 4"라는 이름을 재사용해버렸다(`docs/05-agent-design.md` 참고) — 원래 뜻과 다른 작업에 같은 번호가 붙은 것. 코드에는 `phase=4`가 실제로 존재한 적이 없다(`--phase` 플래그는 계속 `[2, 3]`만 허용). 헷갈리지 않으려면: "Phase 2/3"는 `eval_run.phase` 컬럼에 실제로 저장되는 값(키워드 검색만 vs RAG 포함)이고, "Phase 4"는 순수하게 문서·대화에서만 쓰이는 작업 라운드 이름(안전장치)이다.
