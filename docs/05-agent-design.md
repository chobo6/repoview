# AI Agent 설계 — RepoView

## 1. 도구 목록

| 도구 | 인자 | 반환 |
|---|---|---|
| `list_directory` | `path` | 해당 디렉토리 하위 목록 |
| `search_code` | `pattern`, `path_glob?`, `max_results?` | 파일:라인 + 매칭 라인 컨텍스트 (순수 Python 정규식) |
| `search_semantic` | `query`, `top_k?`(기본 5) | 유사 코드 청크 + 파일:라인 (Chroma, Phase 3부터) |
| `read_file` | `path`, `start_line?`, `end_line?` | 파일 내용 (기본 최대 200줄) |

### `get_repo_overview`를 도구에서 뺀 이유

레포 개요(언어/프레임워크 + depth 2 디렉토리 트리)는 어떤 질문이든 항상 필요한 고정 정보이므로 **시스템 프롬프트에 미리 주입한다.** 도구로 두면 매 질문마다 동일한 결과를 얻기 위해 1턴을 낭비하고, 프롬프트 앞부분이 고정되지 않아 OpenAI 자동 프롬프트 캐싱도 적용받지 못한다. 더 깊은 탐색이 필요하면 `list_directory`로 파고든다.

초기 구상의 7단계 흐름 중 1번("프로젝트 구조 확인")은 도구 호출이 아니라 **프롬프트에 이미 주어진 상태**로 시작한다.

### 도구 인자는 신뢰 경계

모든 도구의 `path` 인자는 LLM이 생성한다. 각 도구는 인자를 레포 루트 기준으로 resolve한 뒤 루트 밖을 벗어나면 거부한다(`../../etc/passwd` 류 차단).

### 검색 전략 안내 (Phase 3)

`search_code`와 `search_semantic`은 역할이 다르다 — `search_code`는 정확한 용어(함수명·SQL 키워드 등)를 알 때, `search_semantic`은 개념은 있지만 정확한 이름을 모를 때 강하다. 모델 판단에만 맡기면 `search_semantic`을 아예 안 쓸 수 있고, PRD의 핵심 성공 기준인 "Phase 2→3 탐지율 개선"을 증명할 수 없게 된다. 그래서 시스템 프롬프트에 다음 지침을 명시한다.

> "먼저 `search_code`로 찾아보고, 결과가 없거나 부족하면 `search_semantic`을 사용하세요."

## 2. 루프 구조

```python
messages = [system_prompt, user_question]

for step in range(MAX_ITERATIONS):        # 기본 15
    response = llm.call(messages, tools)
    record_trace(LLM_CALL, response)

    if not response.tool_calls:
        return response.content            # 정상 종료

    for call in response.tool_calls:
        result = dispatch(call)            # 실패해도 예외 대신 에러 문자열 반환
        record_trace(TOOL_CALL, call, result)
        messages.append(tool_result)

return partial_result(status="CAPPED")     # 상한 도달
```

도구 실행 실패(파일 없음, 검색 타임아웃)는 예외로 전파하지 않고 에러 메시지를 `tool_result`로 돌려준다. 에이전트가 스스로 다른 경로를 시도해 복구할 수 있게 하기 위해서다.

## 3. 종료 조건 — 3중 안전장치

1. 모델이 도구 호출 없이 텍스트만 반환 → 정상 종료
2. `MAX_ITERATIONS`(**6**턴, `REPOVIEW_MAX_ITERATIONS`로 오버라이드 가능) 초과 → `CAPPED`, "여기까지 찾은 것" 부분 결과 반환
3. 누적 토큰 상한(**50,000**) 초과 → `CAPPED`

**판단 이유 (2026-09-12, Phase 4 브레인스토밍)**: 초안은 15턴/200K 토큰이었으나, 예산이 넉넉하지 않아 케이스당 비용이 커지는 쪽보다는 지금 3턴보다 약간의 탐색 여지만 더 주는 쪽으로 낮췄다. 대화 기록이 매 반복 통째로 다시 전송되므로 반복이 늘수록 호출당 비용도 같이 커진다 — 토큰 상한도 15턴 기준(200K)이 아니라 6턴 기준으로 비례해 낮췄다. `read_file`이 이미 최대 200줄로 잘려 나가 단일 호출이 폭주할 일은 적지만, 검색 결과가 예상보다 크게 나오는 등의 예외 상황에 대한 두 번째 방어선으로 유지한다.

### 동일 호출 반복 감지

`run_session`의 루프 안에서 `(tool_name, args)` 조합의 등장 횟수를 세는 딕셔너리를 지역 변수로 유지한다(별도 테이블·상태 저장 불필요). 같은 조합이 3번째 나오면, 도구는 정상적으로 실행하되 그 `tool_result`에 다음을 덧붙인다.

> "이미 동일한 검색을 수행했습니다. 다른 접근을 시도하거나 결론을 내리세요."

에이전트가 같은 검색을 맴도는 것은 가장 흔한 실패 모드이고, 하드캡만 두면 반복 상한을 모두 소진한 뒤 빈손으로 끝난다. 반복을 감지해 방향을 바꾸도록 유도하는 편이 결과와 비용 모두에 유리하다 — 특히 반복 상한이 6턴으로 빠듯해진 만큼, 낭비되는 턴을 줄이는 효과가 더 커졌다.

## 4. 인용 강제 + 사후 검증 (할루시네이션 방지)

**프롬프트 규칙**: 모든 지적은 `파일경로:라인` 형식의 근거를 포함해야 하며, 실제로 읽지 않은 파일은 인용하지 않는다.

**후처리 검증**: `final_review`가 확정되면 `eval_citations.py`의 인용 추출 로직을 재사용해 `파일:라인` 패턴을 정규식으로 뽑아낸 뒤 다음을 대조한다.

1. 해당 경로가 `repo_file` 테이블에 실제로 존재하는가
2. 라인 번호가 그 파일의 길이 범위 안인가
3. 그 파일을 이번 세션에서 실제로 `read_file` 했는가 — 새로 기록할 것 없이 기존 `trace_step`(type=TOOL_CALL, tool_name=read_file)의 `tool_args`/`tool_result`를 대조해서 판단한다

어긋나는 인용이 있으면 `session.citation_warnings`(JSON, 문제 없으면 NULL)에 기록한다.

**판단 이유 (2026-09-12)**: 원래 계획은 "UI에 경고 배지를 달거나 재생성을 요청"이었지만, 이번 라운드는 검증 결과를 **기록하는 것까지만** 한다 — 리뷰를 자동으로 재생성하면 LLM 호출이 추가로 나가 비용이 늘고, 프론트엔드에 배지를 그리는 화면 작업은 별도 스코프로 미뤘다(백엔드 데이터가 준비된 뒤 한 번에 처리하기로 함). eval 관점에서는 "이 세션에 검증 실패 인용이 있었는지" 데이터만 있으면 당장 충분하다. 프로그램적으로 검증 가능한 부분은 LLM을 믿지 않고 코드로 검증한다는 원칙은 유지한다.

## 5. 컨텍스트 관리

- `read_file`은 라인 범위 지정을 권장하고 기본 200줄 상한을 둔다. 전체 파일을 그대로 반환하면 컨텍스트가 빠르게 소진된다.
- `search_code` 결과는 상위 20건까지만 반환한다.
- 시스템 프롬프트는 `[역할 + 레포 개요 + 도구 지침 + 인용 규칙]` 고정 블록을 앞에 두고 사용자 질문을 뒤에 배치한다. 앞부분이 고정되어야 프롬프트 캐싱이 적중한다.

## 6. 시스템 프롬프트 구성

```
[역할]        코드 리뷰 에이전트. 주어진 도구로 근거를 직접 확인한 뒤 답한다.
[레포 개요]   언어/프레임워크, depth 2 디렉토리 트리, 파일 수
[도구 지침]   각 도구를 언제 쓰는지, read_file은 범위를 좁혀 호출할 것,
              search_code 먼저 시도하고 부족하면 search_semantic 사용 (Phase 3부터)
[인용 규칙]   파일:라인 근거 필수, 읽지 않은 파일 인용 금지, 모르면 모른다고 답할 것
[출력 형식]   발견 항목별로 { 문제, 근거(파일:라인), 영향, 제안 }
──────────── 이 위까지 고정(캐싱 대상) ────────────
[사용자 질문]
```
